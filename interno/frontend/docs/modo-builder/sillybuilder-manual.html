01 · QUÉ ES SILLYBUILDER

SillyBuilder es un editor visual de bloques (estilo Scratch) que vive dentro de SillyQuiz. Permite crear "modos": quizzes, juegos de concursantes, pantallas multi-display y experiencias interactivas, sin escribir una línea de código.

En lugar de programar a mano, arrastras bloques desde una paleta, los encajas como LEGO y defines qué pasa cuándo. El resultado no se interpreta en caliente: se compila a una máquina de estados JSON pura (AOT = Ahead-Of-Time) que el backend de Python valida de un golpe y ejecuta de forma determinista durante el show.

IDEA CENTRAL — El builder es un compilador visual. Tú dibujas el árbol de bloques; el compilador AOT lo convierte en JSON; el runtime (en el navegador o en el backend) lo ejecuta como una máquina de estados. Cero interpretación perezosa en medio del directo.

¿Para qué sirve?

  • Quizzes en vivo: preguntas, temporizadores, respuestas de concursantes, puntuaciones.
  • Juegos de concursantes: strikes, rankings, avatares, bonus, eliminaciones.
  • Multi-display: enviar payloads a pantallas NDI o displays sincronizados.
  • Mini-juegos 2D: sprites, físicas, animaciones, colisiones.
  • Experiencias interactivas: eventos de hardware, broadcasts, persistencia SQLite.

El sistema se divide en tres capas que hablan entre sí mediante JSON y WebSockets.

Cada bloque se define con la fábrica def(opcode, category, type, text, args, meta) en scratch-blocks.js:61. Un bloque es una unidad atómica con forma, color, entradas y comportamiento.

Argumentos, campos y sombras

Cada token [TOKEN] en el texto del bloque mapea a una entrada en args. Los tipos de entrada definen cómo se edita y qué acepta:

Tipos de entrada

number, slider, boolean, dropdown, textarea, string, input, id, display_id, output_id, source_id, player_id, audio_file, image_file, reporter, matrix

Meta del bloque

returns, exec(event|sync|async), sideEffects[], bodies[], scope, disabledInProd

Puertos (PORT)

number, string, boolean, color, ndi, display, any — colorean el enchufe y validan compatibilidad.
COMPATIBILIDAD DE PUERTOS — portsCompatible(src, dst) permite conectar si cualquiera de los dos lados es any. Es decir: un reporter any entra en cualquier hueco.

07 · EL RUNTIME (EJECUTOR)

scratch-runtime.js toma la máquina JSON compilada y la ejecuta. Diseño clave: iterativo y con cola explícita (no recursivo) para nunca volar el stack, más un presupuesto de pasos anti-cuelgue.

Cómo arranca

// scratch-runtime.js:388
start(eventOpcode, scripts, eventCtx) {
  // toma la cadena del hat, arma un ctx con state/eventCtx/runtime
  // y llama a executeChain
}

executeChain — la cola

Cada "frame" es {node, next, scope}. Se drena secuencialmente. Si un bloque es asíncrono (wait_seconds), devuelve una promesa setTimeout y el bucle espera. Los errores que no sean break/continue se capturan y se continúa (fronteras de error).

Control de flujo

runContainer maneja los bloques tipo c: if_then, if_then_else, repeat_times, repeat_until, for_each_in_list, repeat_for_range, for_each_with_index, while_loop, try_catch_fallback. Los scopes se apilan/desapilan con _pushScope/_popScope; las variables locales se buscan de adentro hacia afuera y caen al global ctx.state.

Señales y eventos

  • BreakSignal / ContinueSignal — los lanzan break_stack, exit_loop, continue_loop.
  • emit_event → reinicia la cadena on_custom_event.
  • broadcast / broadcast_and_wait — side-effects (devuelven {ok:true}).
  • Engine events: attachEngineEventSource escucha 'engine_event' y arranca engine_on_client_event.

Variables, listas y estado

Se guardan en ctx.state con prefijos semánticos:

var_<NAME>
Variables globales.
score_<PLAYER>
Puntos por concursante.
list_<NAME>
Listas/arrays.
persist_<KEY>
Persistencia SQLite.
alive_<PLAYER>
Estado vivo/muerto.

Física integrada

stepPhysics(dt) integra gravedad y resuelve colisiones AABB (_resolveCollisions). Se ejecuta cada 10 bloques cuando state.__physics está activo.

Providers — el puente con el backend

ScratchRuntime.defaultProviders() son stubs seguros en navegador (math, listas, scores, reporters de quiz, side-effects que devuelven {ok:true}). En producción, el backend sobreescribe reporter / boolean / sideEffect con la lógica real (NDI, displays, estado persistente).

Debugging

  • Breakpoints: setBreakpoint.
  • Step into/over/out.
  • Watch expressions: _evalWatchExpr (evaluador simple de state.).
  • Hooks onBlockStart/onBlockEnd/onError alimentan el Visual Stepper del editor.

08 · EL COMPILADOR AOT

scratch-aot.js convierte el árbol de instancias de bloques en una máquina de estados JSON pura. Sin límites artificiales: se eliminaron MAX_CHAIN y MAX_NESTING — bloques y anidación ilimitados.

compile()

// scratch-aot.js:117
compile(scripts, opts) {
  // scripts = { "<hatOpcode>": [cadena de instancias] }
  // valida que cada clave sea un bloque 'hat'
  // serializa cada cadena → events[hatOpcode]
  return {
    version: 2, compiledAt, engine:'scratch-aot',
    blockCount, events, hotReload, preserveState, snapshotRef
  };
}

_serialize — el corazón

Recorre recursivamente: coerce los args (_coerce), serializa los bodies de los contenedores, sigue next. Cada nodo queda como {opcode, args, [bodies], next, _id}.

validate()

Camina el árbol y chequea: opcodes desconocidos, bloques disabledInProd, y compatibilidad de tipos reporter/boolean. En producción es estricto.

hotReload()

hotReload(prevMachine, scripts, opts) recompila preservando snapshot y estado. Permite editar un modo mientras corre sin perder la puntuación en vivo.

COERCIÓN — Los números vacíos caen al default (0); los booleanos aceptan true/'true'/1/'1'; los dropdowns invalidos vuelven al primero; strings vacíos al default o ''.

10 · INTEGRACIÓN CON EL BACKEND (WS :8081)

El editor abre ws://<host>:8081. Hay dos conexiones WS en paralelo:

  • Live-sync (_initLiveSync): manda el estado del editor a displays/SillyVisualizer.
  • Engine WS (_attachEngineEventSource): gated por token localStorage['sillyquiz-engine-token'].

Mensajes que el builder RECIBE (handleWS)

project, theme, template, sprite, sprite_update, sprite_delete, variable, list, block_def, theme_list, project_list, template_list, save_ok, save_as, error.

Qué hace el backend (websocket_server.py)

asyncio + websockets, 200 conexiones máx, 64KB msg, JWT auth, heartbeat 25s, rate-limit por token-bucket. El handler conmuta por mtype:

13 · MINI PROGRAMA: "QUIZ RELÁMPAGO"

Vamos a construir un mini programa completo que: al iniciar el modo saluda, carga la primera pregunta, y cuando un concursante pulsa el buzzer, suma puntos si acierta y muestra confeti. Sin dejar nada en el aire.

Paso 1 — El disparador (hat)

⚡ AL INICIAR MODO

El hat on_mode_init arranca la cadena. Todo modo empieza aquí.

Paso 2 — Preparar el escenario

⚡ AL INICIAR MODO 🎨 PON TEMA "silly-quiz" 🔊 TOCA MÚSICA DE FONDO 🧠 INICIAR QUIZ

set_theme (looks), play_bg_music (audio) y init (quiz) preparan el estado base. init carga el primer set de preguntas.

Paso 3 — Cargar pregunta y temporizador

⚡ AL CARGAR PREGUNTA 🧠 TEXTO PREGUNTA → ESCENARIO ⏱ TEMPORIZADOR 15s

El hat on_question_load reacciona cada vez que se carga una pregunta. Mostramos el texto y armamos un timer de 15s.

Paso 4 — Reaccionar al buzzer

⚡ AL PULSAR BUZZER 🔧 SI < respuesta correcta? > ▸ 👥 +10 PUNTOS AL JUGADOR 🎮 CONFETI 🔧 SINO ▸ 👥 STRIKE AL JUGADOR

on_player_buzz captura el evento de hardware (vía cola FIFO del backend). El if_then_else (tipo c) evalúa el reporter booleano verify_answer. Si acierta: add_score + anim_confetti; si no: strike.

Paso 5 — Tiempo agotado

⚡ AL EXPIRAR TEMPORIZADOR 🧠 REVELAR RESPUESTA 🧠 SIGUIENTE PREGUNTA

on_timer_expire revela la respuesta correcta y pasa a la siguiente. El bucle del quiz se auto-alimenta.

El programa completo (máquina AOT resultante)

{
  version: 2, engine:'scratch-aot', blockCount: 12,
  events: {
    "on_mode_init": [
      { opcode:"set_theme", args:{ theme:"silly-quiz" } },
      { opcode:"play_bg_music", args:{} },
      { opcode:"init", args:{} }
    ],
    "on_question_load": [
      { opcode:"question_text", args:{} },
      { opcode:"timer_set", args:{ seconds:15 } }
    ],
    "on_player_buzz": [
      { opcode:"if_then_else",
        args:{}, bodies:{
          body:[ { opcode:"add_score", args:{ points:10 } },
                 { opcode:"anim_confetti", args:{} } ],
          elseBody:[ { opcode:"strike", args:{} } ]
        },
        next: null }
    ],
    "on_timer_expire": [
      { opcode:"reveal_answer", args:{} },
      { opcode:"next_question", args:{} }
    ]
  }
}

¿Cómo funciona en ejecución?

  1. El runtime arranca on_mode_init → pinta tema, música, init.
  2. init dispara internamente on_question_load → texto + timer 15s.
  3. Un concursante pulsa buzzer → backend encola hardware_event → runtime ejecuta on_player_buzz.
  4. El if_then_else evalúa verify_answer: si true → +10 y confeti; si false → strike.
  5. A los 15s, on_timer_expire revela y pasa a la siguiente pregunta → vuelve al paso 2. Bucle infinito controlado.
  6. En cualquier momento, builder_state emite el estado a las pantallas NDI conectadas vía WS :8081.
DETERMINISMO — Todo esto corre sobre la máquina JSON validada por AOT. No hay interpretación en caliente: lo que ves al editar es exactamente lo que corre en el show.

14 · CABOS SUELTOS (Y SUS RESPUESTAS)

Para no dejar nada colgando, aquí están las irregularidades conocidas y dónde viven:

1. Categorías HTML vs Registro — El sidebar tiene 18 pestañas; el registro 17. Las 7 extra (motion, sound, sensing, network, storage, ui, media) son legacy/placeholder sin bloques.
2. inject_css_raw — Está comentado y bloqueado por seguridad (inyección arbitraria de CSS). No está activo pese a aparecer en grep de def(.
3. Dos WS en paralelo — Live-sync (:8081) y Engine WS (token-gated). No son lo mismo.
4. Providers por defecto — Los stubs del runtime son seguros; la lógica real (NDI, displays, persistencia) la inyecta el backend vía providers.
5. BlockRegistry vs ScratchBlocks — El HTML importa BlockRegistry pero el objeto real es window.ScratchBlocks. Usa ScratchBlocks.
6. Globals externos — TemplateMigration, SillyPackage, SillyAssetSanitizer viven en archivos JS no-scratch-* del mismo directorio. Se encargan de migración de plantillas, empaquetado .silly y saneamiento de assets respectivamente.
